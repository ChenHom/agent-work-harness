## A. 值得優先看的兩點

### A-1 read-only 模式的 network deny 從沒被實測過
**提出者**：user02 ｜ **Owner 核對**：已核對，屬實

`src/runtime/isolation.ts` 的 `CODEX_CONFIG` 只在 `[sandbox_workspace_write]` 區塊寫
`network_access = false`，而且旁邊的註解本身就寫著「spike 實測：未顯式關閉時 curl 仍可連外，
因此必須寫死 false」。

`docs/spikes/2026-08-21-isolation-spike.md` 的探測表（含 `curl` → DENIED）確實是在 workspace-write
下做的；文件第 44 行的 `-s read-only` 另行 probe 只重跑了「workspace 內寫檔 → DENIED」一項，
**沒有重跑網路探測**。

如果 codex 對 `-s read-only` 走另一套 sandbox profile、不讀 `[sandbox_workspace_write]` 這個
section，read attempt 的網路可能仍然是通的。workspace 裡若有 repo 自己的 `.env` 或 API key，
這就是一條沒被驗證封死的外洩路徑。

建議：比照 workspace-write 那組，對 `-s read-only` 補一次 curl 探測。成本很低，
而且是把「假設擋住」換成「實測擋住」——與 D-04~D-06 全部標 `[實測]` 的既有標準一致。

### A-2 agent 側只實測了寫入邊界，沒實測絕對路徑讀取
**提出者**：user02 ｜ **Owner 核對**：已核對 spike 文件的探測項目，屬實

spike 的探測項目是 workspace 內／外寫檔、curl、`printenv HOME`、`ls -a $HOME`。
其中 `ls -a $HOME` 因為 HOME 已被重導向，本來就看不到東西——但那證明的是 env var 改了，
不是檔案系統邊界存在。

workspace-write 類 sandbox 常見的設計就是「寫入受限、讀取不受限」。目前沒有一條探測回答
「codex exec 用絕對路徑 `cat /home/hom/.secrets` 會怎樣」。D-05 說擋掉了操作者的其他 credentials，
但擋法是 HOME 隔離，跟絕對路徑讀取是兩件事。

建議：補一條絕對路徑讀取探測。這一點與 A-1 是同一類——**已經有的隔離結論都是實測出來的，
只有這兩個角落還停在假設**。

## B. 有道理但可以等的

### B-1 Runtime 抽象目前主要服務測試，還不足以證明可替換 agent runner
**提出者**：user03 ｜ **Owner 核對**：已核對，屬實

`src/orchestrator.ts:100` 的 driver 雖然可注入，預設仍是 `new CodexDriver(policy)`；
`:238` 建立 attempt 時 `runtime` 寫死 `'codex'`；`:303` 輸出固定走 `parseRuntimeResult()`。

README 講的「跨兩種語言／domain／runner，Core 0 修改」，現有證據涵蓋的是 **repo 與 verification
runner** 的差異，**尚未涵蓋第二種 agent runtime**。

user03 自己的建議是「暫不為假想 runner 重構」，等真要接第二個 runtime 時，再讓 driver 自帶
`id + prepare/run + parseResult`，由 bootstrap registry 選擇。這個判斷跟 README 上
「不為了把清單清空而實作」的立場一致。

Owner 註：這一點的價值不在改 code，在於**README 的措辭**。目前的寫法容易讓讀者以為 agent runner
也換過了。把「runner」講明是 verification runner，比重構划算得多。

### B-2 evidence 橫向依賴到 codex 專屬的隔離模組
**提出者**：user03 ｜ **Owner 核對**：未核對

`src/evidence/exec.ts` 直接從 `src/runtime/isolation.ts` 取 `bwrapArgv`、`verificationEnv`，
而後者同檔還承載 Codex config、auth copy、agentEnv。目前沒有造成錯誤，但 evidence 已間接依賴
特定 agent runtime 的檔案。

建議是把通用的 bwrap／verification sandbox 拆成中性模組，Codex 專屬的留在 `runtime/codex-*`。
與 B-1 綁在一起——真的要接第二個 runtime 時再一起做，單獨做價值不大。

### B-3 verification completeness 的退化沒有被契約看見
**提出者**：user03 ｜ **Owner 核對**：已核對 parser 範圍，屬實

`src/evidence/verification.ts` 的 `parseCompleteness()` 只內建兩種 parser：node:test
（`ℹ tests 80`）與 pytest（`5 passed, 2 skipped`）。`docs/cross-repo-validation.md` 已記錄
task-tracker 的自訂串接與 rag-stack 的 unittest 都退化成 exit-code fallback。

也就是說：**兩站跨 repo 驗證，completeness 這一層實際上都沒有生效**，而 Repository Contract
上看不出來這件事。

user03 的建議是若第三站再遇到同樣情形，就把「completeness 是否可觀測」顯式放進 Repository
Contract（宣告無／既有 parser／受限的 JSON summary），而不是擴大猜輸出的 regex。
這保留了 fail-closed 原則，也讓保護強度可被契約看見。

## C. 驗證與 evidence 路徑的四點

全部由 user04 提出。

### C-1 git probe 失敗被當成空 diff
**Owner 核對**：已核對，屬實

`src/evidence/git.ts` 的 `observeGit()` 裡，只有 `git rev-parse HEAD` 檢查了 `exitCode`；
`git status`、`git diff --name-only base..head`、`git diff base` 三個呼叫都只取 `stdout`，
非 0 exit 與 stderr 沒有進 evidence。

後果：git probe 掛掉時，harness 看到的是「沒有變更」，而不是「我沒看清楚」。
對一個以「自己收集 evidence 判定成敗」為核心立場的工具，這是最不該有的失敗模式——
**它會把觀測失敗誤讀成觀測到乾淨**。

建議：把 git probe 改成 structured result，任何 probe 失敗直接產生 INCONCLUSIVE 或 FAIL。

Owner 註：這點雖然列在 C，但性質上跟 A 那兩點一樣是「fail-closed 有洞」，
如果只做一件事，我會先做這個。

### C-2 git evidence 沒有顯式關掉外部 diff driver
**Owner 核對**：已核對，屬實

`src/evidence/git.ts` 的 `git diff` 呼叫沒有帶 `--no-ext-diff` / `--no-textconv`。
D-06 已經承認 `.gitattributes` 的 textconv 能執行程式碼——所以才把 git evidence 也放進 bwrap。
既然已經認知到這個風險，在 bwrap 之外再加一層 `--no-ext-diff` 是幾乎零成本的縱深防禦：
避免 evidence 取樣本身還能觸發 repo 控制的指令。

### C-3 contract hash 沒涵蓋合併後的有效邊界
**Owner 核對**：已核對，屬實

`src/repo/contract.ts:92` 的 `loadSnapshot()` 會把 `policy.defaultProtectedPaths` 與 contract
自己的 `protectedPaths` 合併，但 `:97` 的 hash 算的是 raw config text。

後果：global policy 改了 → 有效的 protected path 集合變了 → **contractSnapshotHash 不變**。
審計上看不出邊界動過。這跟「config 在 attempt 前被 hash 凍結，agent 改不了自己的驗收規則」
這個賣點是有落差的——凍住的是宣告，不是有效值。

建議：另存 effective snapshot fingerprint，或至少把 policy 版本寫進 attempt/evidence。

### C-4 baseline 與正式 verification 的管線重複
**Owner 核對**：已核對，屬實（`collectBaseline` 在 `:96`、`runVerification` 在 `:125`，共用 `runCheck`）

兩者其實是同一條 runner 管線，但命令執行、completeness 解析、tail 格式化各寫一份。
建議抽 `runVerificationCheck()` / `formatVerificationEvidence()` 共用，
之後加新 check kind 或改解析規則時不容易 drift。

四點裡這是唯一純粹的整潔問題，優先度最低。

## D. prompt 編譯與 context manifest 的四點

全部由 user05 提出。這是 harness 最核心的機制，前三題都沒有碰到。

### D-1 deterministic 是「Manifest → prompt」成立，不是 end-to-end
**Owner 核對**：已核對，屬實

`src/prompt/compiler.ts` 本身沒有時間戳或隨機值，`test/compiler.test.ts` 也證明同樣輸入產出同樣
text/hash。但上游的 `src/context/manifest.ts:14` 每個 ContextItem 都帶 `id: newId('CI')`——**隨機 id**。

再加上 compiler 直接沿用 `decisions`、`previousEvidence`、`approvedSkills` 的輸入順序，
而 store 的列表查詢只 `ORDER BY created_at / observed_at`，**時間戳相同時順序未定**。

建議：列表查詢加 id 當 tie-breaker，並在文件與測試裡明確區分「prompt deterministic」與
「manifest deterministic」——目前 README 講的 deterministic 讀起來像是後者，實際只保證前者。

### D-2 context budget 沒有計入模板 overhead，超限也沒有訊號
**Owner 核對**：未核對

budget 目前只算 Manifest item 的字元數，六區固定模板與 AUTHORITY / OUTPUT CONTRACT 的字元
不在內。而且 P0 加上最後一個 pointer 仍超限時照樣回傳，caller 只記 dropped，沒有 over-budget 訊號。

建議：讓 budget 以最終 compiled prompt 為準扣掉保留 overhead，或至少回傳 `overBudget` / `remaining`
並寫進 attempt evidence。否則會出現「budget 欄位看起來正常，prompt 實際已超上限」而不易察覺。

### D-3 provenance / trust 的契約沒有落到 compiler
**Owner 核對**：已核對，屬實

`manifest.ts` 產生了 control / source / trust / priority 這些欄位，但 `compiler.ts` **完全沒有渲染
`manifest.control`**——它反而從 raw contract 與 authority 重組。`decisions`、`userContext`、
`previousEvidence` 也只取 `content`，沒有驗證 kind / trust / source。

目前正常 producer 的結果仍可工作，但這代表兩件事：未來新增 P0 control item 會**靜默遺失**；
錯誤放進 decisions 的 untrusted item 會被當成 USER DECISIONS 渲染進 prompt。

建議：由單一 typed renderer 以 Manifest 為輸入並在邊界驗證 kind / trust，或者乾脆刪掉沒被使用的
control 欄位——留著一個沒人讀的 trust 欄位，比沒有更危險。

### D-4 pointer 的 denied filter 只做字串完全相等
**Owner 核對**：已核對，屬實

`src/context/manifest.ts:34-36` 是 `const denied = new Set(contract.deniedPaths)` 加上
`.filter((p) => !denied.has(p))`——**完全相等比對，glob 不生效**。

具體後果：deny 寫 `payment/**`、使用者明確提到 `payment/src.ts` 時，該 path 仍會出現在
Suggested entry points 裡。prompt 裡的 `Inspect additional repository files as needed` 也意味著
pointers 是建議而非硬邊界。

建議：改用 glob overlap 過濾 denied / protected 底下的 pointer，並在文件裡講明 pointer 到底是
導覽提示還是 hard scope；補一組 nested denied path 的測試。

## Owner 的取捨

按「這一點是否讓 harness 對自己說謊」排序，不是按工作量：

1. **C-1**（git probe 失敗當成空 diff）——觀測失敗被誤讀成觀測到乾淨，直接違背核心立場
2. **D-4**（denied filter 字串相等，glob 不生效）——authority 邊界沒有真的守住，且修法明確
3. **A-1 / A-2**（read-only 網路、絕對路徑讀取沒實測）——補兩條 probe，把假設換成實測
4. **C-3**（contract hash 沒涵蓋有效邊界）——凍結的是宣告不是有效值，與賣點有落差
5. **D-1**（deterministic 只到 Manifest→prompt）——修法便宜（id tie-breaker），主要是把宣稱講準
6. **C-2**（`--no-ext-diff`）——幾乎零成本的縱深防禦
7. **D-3**（trust 欄位沒人讀）——留著沒被驗證的 trust 欄位比沒有更危險，刪掉或落實二選一
8. **B-1 的 README 措辭**——不用改 code，只要把「runner」講清楚
9. 其餘（B-2、B-3、C-4、D-2）——維持 watch list，等觸發條件出現

值得注意 C-3 與 D-4 是同一種病：**宣告的邊界與有效的邊界不一致**。
C-3 是 hash 凍住了宣告卻沒凍住 policy 合併後的有效值，D-4 是 deniedPaths 宣告了 glob
卻用字串相等在比。兩者都不會讓 harness 崩，只會讓它以為自己守住了。

B-3 特別值得留意：它不是一個要不要實作的問題，而是**兩站跨 repo 驗證裡 completeness 都沒生效**
這個事實目前沒有被記錄在任何契約上。就算不改 code，把這件事寫進
`docs/cross-repo-validation.md` 也是有價值的。

## 附註：為什麼少了 CLI 使用體驗那一份

CLI 體驗這題派給 user06，他的 runner 是 AGY（`Gemini 3.7 Flash (High)`）。三次嘗試都以
「exit 0、零輸出」收場，一則留言都沒留下，原因是 AGY headless 的工具權限模型：

`agy --print` 無法互動確認，`~/.gemini/antigravity-cli/settings.json` 的 `permissions.allow`
以外的每一個指令都會被 soft-deny，然後**整個 session 直接放棄**。三次分別倒在不同的指令上：

| 次數 | 被拒的指令 | 缺的規則 |
|---|---|---|
| 1 | `node -e '…'`（解析 API 回應） | `command(node)` |
| 2 | `pwd && curl …`（複合指令，兩端都要放行） | `command(pwd)` |
| 3 | `curl … \| jq …`（管線，兩端都要放行） | `command(jq)` |

同一份題目、同一個 runner，每次換一種寫法就撞到一個新的缺口。這不是 harness 的問題，
是評審這一側的工具限制，記在這裡是為了說明**這份文件的覆蓋範圍為什麼有一塊空的**。

對照組：另外三位成員用 codex（sandbox 是能力邊界，沒有指令白名單）與 claude
（有 Read/Glob/Grep 這類非 shell 的檔案工具），都沒有遇到這個問題。
